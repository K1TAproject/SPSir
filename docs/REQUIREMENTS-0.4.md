# Request：0.4 公共事件、多人 AA 与个人流水联动

状态：已实现并完成开发验证，待实体手机试用  
日期：2026-10-04  
项目：SPSir（随手账本）  
基线：当前 0.3.1，本文件建议作为下一阶段 0.4 的开发需求

## 1. 背景与目标

现有事件只归集软件用户自己的支出，录入金额默认已经 AA。本版增加“公共事件”：用户在一台手机上添加同行人员，记录每笔费用的付款人和参与分摊者，由软件计算各人的承担金额及事件结算方案。

例：三人旅行，用户支付一笔 1,200 元住宿，三人均分。事件记住宿总额 1,200 元，用户个人流水只记 400 元；同行者应承担的部分不进入用户的消费统计。若之后同行者支付餐饮等费用，系统综合所有费用计算最终谁应转给谁多少钱。

成功标准：一份公共费用数据能同时支撑事件总额、成员分摊、转账建议和用户个人流水，并且新增、修改、删除及备份恢复后，所有金额始终一致。

## 2. 已确认范围与建议边界

### 2.1 用户已确认

- 暂时搁置支付识别、自动提示记账功能。
- 本版先做单机多人分摊，由软件用户录入；多人登录与跨设备共同编辑留待后续。
- 公共事件能够添加同行人员，并选择各笔开支的参与者。
- 需要计算每个人应承担的总额，以及根据实际付款情况生成最终转账结算建议。
- 软件用户本人承担的消费自动进入个人流水。

### 2.2 本文建议采用的首版边界

- 每笔费用由一人付款，可以为任意一名事件成员；付款人不一定参与消费。
- 选择具体成员后均分，不只填写人数；人数由选中成员自动得到。
- 仅自己承担或仅其他一人承担，均视为选择一名参与者，无需单独模式。
- 本版暂不支持按比例、按权重、自定义各人金额或一笔费用多人付款。
- 结算统一按用户手动填写的人民币金额计算，不自动获取汇率。
- 生成转账建议，不执行支付、不读取银行账户，也不记录实际转账完成情况。
- 不扩展群聊、邀请链接、通讯录权限、云端账号、预算或账户余额。

本版按上述边界实现。不均分、多付款人或实际结算完成状态可在后续版本另立需求。

## 3. 概念和金额口径

| 概念 | 定义 | 是否进入个人消费统计 |
|---|---|---|
| 公共事件 | 在当前手机中记录多名成员费用的事件 | 仅本人份额进入 |
| 事件成员 | 事件中的人员，包含且仅包含一个“我” | 成员本身不产生流水 |
| 付款人 | 为该笔费用实际支付全部金额的人 | 不按付款总额直接计入 |
| 分摊参与者 | 实际承担该笔费用的成员集合 | 本人在集合内时计入本人份额 |
| 项目总额 | 该笔消费的完整费用 | 用于事件总额 |
| 我的支出 | 本人在该笔消费中承担的金额 | 是 |
| 已付 | 成员直接支付给商家等收款方的项目费用合计 | 不等于个人消费 |
| 应承担 | 成员在所有费用中的分摊份额合计 | 本人的应承担额对应个人流水 |
| 应收／应付 | 已付与应承担之间的差额 | 不作为普通收入／支出 |

“公共”在本版仅表示多人分摊，不代表联网、公开可见或其他成员可以编辑。建议只在创建类型的简短说明中写“本机记录，多人分摊”，日常页面不反复解释。

## 4. 用户场景与业务规则

### 4.1 创建事件与管理成员

1. 新建事件时可选“个人事件”或“公共事件”。默认个人事件，保留现有快速创建体验。
2. 公共事件自动包含“我”，可添加同行者昵称。无需手机号、账号或通讯录。
3. 每个成员使用稳定 ID 关联数据，昵称仅用于显示；事件内昵称去掉首尾空格后不得重复，建议限制 1～20 字。
4. “我”的身份固定，不能删除或转移给其他成员；其他成员不能命名为“我”。
5. 允许先创建只有“我”的公共事件，随后添加成员。一个人参与的费用正常按一人计算。
6. 修改成员昵称不改变历史份额；改变显示顺序不得改变历史尾差分配。
7. 新成员只影响之后新建费用的默认选项，不自动加入已有费用。
8. 无任何费用引用的成员可删除；已作为付款人或参与者的成员不能直接删除，提示“该成员有关联开支”。本版不做成员退出、归档或级联删除费用。

### 4.2 记录公共费用

必填：项目总额、币种、人民币总额（外币时）、支出细类、日期、付款人、至少一名参与者。备注可选。

- 人民币只填写一次金额；外币沿用“原币金额＋币种＋人民币金额”的手动录入方式，但此处填写整笔费用的总额。
- 付款人默认“我”；参与者默认当前事件全部成员。保存前明确显示选中的人及各自份额。
- 用户可取消本人或其他成员的勾选；禁止无参与者保存。
- 付款人与参与者独立选择。例如“我代付、仅朋友承担”是有效记录。
- 用户没有付款但参与分摊时，仍须将其份额写入个人流水。
- 用户既未付款也未参与时，费用仍进入事件总额和其他成员结算，但不进入用户个人流水。
- 一笔费用使用一个支出细类；混合类别消费需要拆开录入，不在本版增加按成员分类。
- 输入校验延续现有金额精度、单笔上限、日期和备注规则；不同事件的成员不能互相引用。

### 4.3 已 AA 金额与多人付款的处理

新建公共费用的主金额标签必须为“项目总额”，避免误把个人份额再次除以人数。

如果用户只想记录已 AA 的个人消费，应选择“我付款、仅我参与”；该记录只表示个人这部分，不用于还原其他成员的总消费。

若其他人实际垫付、需要计算欠款，应按真实付款人和完整项目总额录入，不得用已 AA 的个人金额代替项目总额。

一笔消费多人付款不在本版直接支持。只有当拆开的各部分本身可被正确描述为独立费用时，才可分别记录，不能让用户随意拆金额后得到错误的分摊结果。

### 4.4 编辑、删除与历史处理

- 修改总额、参与者或付款人后，自动重算受影响费用、成员汇总和结算建议。
- 修改分类、日期、备注后，关联个人流水同步更新；日期变化应反映到日／周／月／年统计。
- 修改付款人只改变已付和结算差额，不改变各人的应承担额。
- 删除费用必须确认，并同时删除相应个人流水；没有本人份额时只删除公共费用数据。
- 从个人流水打开公共费用时进入同一公共费用编辑页，不允许独立修改派生的本人金额。
- 从个人流水请求删除公共费用时提示“删除整笔公共开支？将同步更新所有人的分摊。”，不得用普通个人流水提示掩盖影响。
- 本版不支持已有个人事件直接转换为公共事件，也不自动把旧个人流水推算为团体费用。
- 普通个人流水编辑时，公共事件不能像旧事件一样直接作为普通关联项保存。应明确进入公共费用录入；旧流水迁移到公共事件留待后续。

## 5. 分摊和结算算法

### 5.1 均分与尾差

所有计算使用整数最小货币单位；人民币使用分，不用浮点金额计算。

对金额 M、参与人数 N：

1. 每人基础份额为 M 整除 N。
2. 余数为 M 对 N 取余。
3. 按成员的稳定创建顺序，将余数逐个分配，每人最多增加一个最小货币单位。
4. 同一组数据重复计算必须得到同一结果，不受昵称、勾选顺序或界面排序影响。

例：100.00 元由“我、甲、乙”均分，按上述稳定顺序分为 33.34、33.33、33.33 元。保存前显示实际份额，必要时仅显示简短提示“尾差已分配”。

不变量：所有参与者份额之和严格等于项目总额；非参与者份额为零。极小金额可能使部分参与者分得零份额，不能人为把这些份额抬高为一分。

### 5.2 外币

- 原币总额和人民币总额分别按各自最小货币单位执行同一均分规则，各自保持总和守恒。
- 支持现有币种，包括没有小数位的日元、冰岛克朗；不能统一按两位小数分配原币。
- 例如 NOK 600.00、人民币 400.00，两人均分后各为 NOK 300.00、人民币 200.00。
- 不使用统一汇率重新换算，不将不同原币直接相加；事件合计和结算使用人民币，原币在费用明细中保留。
- 小额分摊可能产生“原币份额为零、人民币份额非零”或相反的舍入结果，内部允许非负派生金额。普通手动记账仍要求正数。
- 若本人原币和人民币份额均为零，不创建个人流水；任一份额大于零时保留一笔关联个人流水，人民币为零时不增加人民币消费合计。

### 5.3 成员汇总

对每个成员 i：

```text
已付 P(i) = 该成员作为付款人的所有项目人民币总额之和
应承担 S(i) = 该成员在所有项目中的人民币份额之和
差额 B(i) = P(i) - S(i)

B(i) > 0：应收 B(i)
B(i) < 0：应付 -B(i)
B(i) = 0：无需转账
```

事件总额 = 所有项目人民币总额之和 = 全体成员已付之和 = 全体成员应承担之和；全体差额之和必须为零。

“我的支出”使用 S(我)，不能使用 P(我)。事件总额包含仅其他成员参与的消费，因此可能大于用户在个人流水中筛选该事件得到的金额。

### 5.4 转账建议

- 将应付成员与应收成员分别按剩余金额从大到小排列，金额相同按稳定成员顺序排列。
- 每次生成一笔“应付成员 → 应收成员”，金额为双方剩余额度的较小值，再更新余额，直到全部归零。
- 结果必须确定、无零元转账，执行所有建议后各人差额均为零。
- 这是有效的净额结算建议，不宣称一定达到数学意义上的全局最少转账笔数；不引入复杂优化求解器。
- 建议可以直接在成员间轧差，不必沿原来的垫付关系逐笔归还。
- 所有金额以人民币显示，不代替真实支付，不要求提供银行卡或收款码。

首版不记录旅途中已经发生的成员间还款，结算区必须用简短提示标明“未扣除成员间已转账”。用户应在费用核对完成后使用建议；已按旧方案转账后若再修改费用，新方案并不是仅剩待付金额。部分结算、转账完成状态及差额补结算另立需求。

成员间 AA 转账不是消费或收入，本版不会把“朋友归还垫付款”添加为普通收入，也不会再次把“我补给朋友的钱”添加为支出。

### 5.5 可核对的完整例子

事件成员为“我、甲、乙”，顺序固定：

| 项目 | 总额 | 付款人 | 参与者 | 我承担 | 甲承担 | 乙承担 |
|---|---:|---|---|---:|---:|---:|
| 住宿 | 1,200.00 | 我 | 我、甲、乙 | 400.00 | 400.00 | 400.00 |
| 晚餐 | 300.00 | 甲 | 我、甲 | 150.00 | 150.00 | 0.00 |
| 出租车 | 90.00 | 乙 | 甲、乙 | 0.00 | 45.00 | 45.00 |
| 胶卷 | 180.00 | 我 | 我 | 180.00 | 0.00 | 0.00 |
| 合计 | 1,770.00 | — | — | 730.00 | 595.00 | 445.00 |

| 成员 | 已付 | 应承担 | 结算 |
|---|---:|---:|---|
| 我 | 1,380.00 | 730.00 | 应收 650.00 |
| 甲 | 300.00 | 595.00 | 应付 295.00 |
| 乙 | 90.00 | 445.00 | 应付 355.00 |

转账建议：乙 → 我 355.00 元；甲 → 我 295.00 元。

用户个人流水新增三笔：住宿 400.00、晚餐 150.00、胶卷 180.00，合计 730.00 元；出租车不产生用户流水。没有任何一笔额外的 650 元收入或 AA 转账支出。

## 6. UI 与交互

沿用松绿色、暖白、陶橙色主题及当前字体、卡片、分类选择和日期控件。新增信息以金额、标签和短操作名称呈现，不增加长篇教学文案。

### 6.1 事件列表与新建

- 新建弹窗：事件名称、类型选择；选择公共事件后显示“我”和添加同行者入口。
- 公共事件卡片标识“公共 · 3 人”，主金额明确写“事件总额”，辅助显示“我的支出”。
- 个人事件继续显示个人金额，避免两种类型共用无口径的“累计支出”标题。

```text
北欧旅行                         公共 · 3 人
事件总额  ¥1,770.00
我的支出    ¥730.00
```

### 6.2 公共事件详情

顶部保留事件名与返回，增加“成员”入口；概览展示事件总额和我的支出。下方仅设置“开支／结算”两个页签，避免首页堆叠所有表格。

```text
〈 北欧旅行                         成员

事件总额  ¥1,770.00
我的支出    ¥730.00

[ 开支 ]   结算

10 月 4 日
住宿                       ¥1,200.00
我付 · 3 人分摊             我 ¥400.00

晚餐                         ¥300.00
甲付 · 我、甲               我 ¥150.00

出租车                        ¥90.00
乙付 · 甲、乙               我未参与

                            ＋ 记开支
```

- 开支页按日期倒序，金额为项目总额；本人份额作为辅助信息。
- 小人数直接显示参与者名字；长名单显示人数，点开费用详情查看完整名单和份额。
- 沿用类别占比时，公共事件明确标为“事件类别占比”，按项目总额计算；个人统计页始终只按个人流水计算。
- 首版不增加事件详情的第二套个人图表，“我的支出”概览和个人流水筛选足够使用。
- 空事件显示“暂无开支”，结算页显示“暂无待结算费用”。

### 6.3 录入与编辑公共费用

复用现有金额优先、数字键盘、分类面板和日历选择体验；新增内容仅为付款人、参与者与分摊预览。示例：

```text
记开支

项目总额       1,200.00
币种           人民币
分类           住宿
付款人         我 ▾
参与者         [✓ 我] [✓ 甲] [✓ 乙]

每人 ¥400.00
我的支出 ¥400.00

日期           2026-10-04
备注           可选

取消                              保存
```

- 付款人用单选，参与者用多选，不能使用同一组控件混淆含义。
- 提供“全选”；只选我即可录个人费用，不额外设计复杂模式切换。
- 有尾差时展开实际成员份额，不能显示一个不精确的统一人均金额。
- 改总额、币种、人民币金额或参与者时，预览即时更新；只有点击保存才写数据库。
- 我未参与时显示“我的支出 ¥0.00”，不隐藏整笔记录。
- 外币标签为“原币总额”“人民币总额”，预览可查看双币份额。
- 保存按钮防重复点击；键盘打开时可滚动、可查看分摊预览并保存。

### 6.4 结算页

```text
[ 开支 ]   结算

成员       应承担       已付         结算
我         730.00      1,380.00     应收 650.00
甲         595.00        300.00     应付 295.00
乙         445.00         90.00     应付 355.00

转账建议
乙 → 我    ¥355.00
甲 → 我    ¥295.00

未扣除成员间已转账
```

- 手机窄屏或大字号时，成员汇总使用纵向卡片，不能强行挤成四列。
- 全体差额为零时显示“无需转账”；有费用时仍保留各人已付与应承担。
- 不显示“已结清”按钮，避免在没有实际还款记录的情况下作出误导判断。

### 6.5 个人流水联动

- 显示本人份额、原支出分类、消费日期及事件名称，可用“公共分摊”短标签识别来源。
- 点击进入公共费用详情；详情中能看到项目总额、付款人及本人份额。
- 从首页新增支出时，选择公共事件后切换到公共费用表单，保留已填写的兼容字段，并将金额标签明确改为项目总额；取消不产生任何数据。
- 普通收入不进入公共费用，也不参与 AA 结算。

## 7. 实现逻辑与数据设计建议

### 7.1 保留当前架构

沿用 Kotlin + Jetpack Compose + Room / SQLite，继续本地优先，不为本版引入服务器、登录 SDK、同步框架或支付 SDK。

当前源码中 `LedgerEvent` 只有 ID、名称；`LedgerEntry` 保存个人金额、分类、日期和事件关联。保留这些字段的原有含义。公共费用作为新增业务数据，不把现有个人金额字段改成团体总额。

### 7.2 最小数据关系

下表是建议的逻辑结构，具体命名可以沿用代码风格，不要求增加通用框架。

| 数据 | 主要内容 | 约束 |
|---|---|---|
| 公共事件扩展 | 关联现有事件 ID | 有扩展记录表示公共事件，无则为原个人事件 |
| 事件成员 | ID、事件 ID、昵称、是否本人、稳定创建顺序 | 每个公共事件恰有一个本人 |
| 公共费用 | ID、事件 ID、付款人 ID、原币总额、币种、人民币总额、类别、日期、备注、可空个人流水 ID | 单一付款人；个人流水关联唯一 |
| 费用参与者 | 费用 ID、成员 ID | 组合唯一，所有人必须属于同一事件 |
| 现有个人流水 | 本人分摊得到的金额及原有字段 | 最多一笔对应一条公共费用 |

份额采用确定的均分规则计算，首版不必另存冗余成员汇总和结算结果。参与者选择、成员稳定顺序和费用总额是计算依据，恢复备份后结果必须相同。

公共费用是事实来源；与之关联的个人流水是供现有筛选和统计使用的派生记录。二者用途不同，不能把公共费用总额再次加入个人汇总。

### 7.3 原子保存与入口约束

每次新增／编辑／删除都在同一个 Room 事务中：

1. 校验事件、付款人、参与者、分类与金额。
2. 保存费用和参与者集合，计算本人份额。
3. 本人有非零份额时，创建或更新同一条个人流水；不重复追加。
4. 本人退出分摊或双币份额均为零时，删除原关联流水并清除关联。
5. 成功提交后刷新事件、个人流水与统计；失败时整笔回滚。

补充约束：

- 新增在保存前生成稳定费用 ID，防止重复点击产生两笔费用。
- 关联个人流水存在时优先复用其 ID；不能每次编辑都删掉再追加。
- 个人流水的通用保存、删除入口必须识别公共费用来源，并路由到公共费用操作，不能绕过关联校验。
- 派生金额允许零的校验只应用于可验证的公共分摊记录，不能直接放宽所有手动流水输入。
- 汇总和分摊计算要避免整数溢出；错误不能被静默截断或转换为负数。
- 计算函数独立于 Compose，方便用真实金额例子验证，但不构建通用分账规则引擎。

### 7.4 原有事件、数据库和备份兼容

- 当前数据库版本为 2；如按本方案实施，新增相应表并提供 2 → 3 的非破坏性迁移，继续保留 1 → 2 路径。
- 所有旧事件继续是个人事件，旧流水金额、ID、分类和日期不变。不推测同行者、总额或历史付款人。
- 迁移时不清库，不自动重算旧消费，也不创建公共费用副本。
- 当前 JSON 备份版本为 1；新版导出应提高格式版本并包含公共事件、成员、费用、参与者和个人流水关联。
- 新版 APP 能读取旧版备份：将其还原为原个人账本；旧版 APP 不要求读取新版备份。
- 恢复前校验本人唯一、跨事件引用、参与者唯一、金额范围、关联流水唯一及派生金额一致性；不一致时拒绝恢复，不悄悄修正。
- 备份必须保留用于尾差分配的成员稳定顺序；恢复前后份额和转账建议一致。
- 延续覆盖前安全副本和事务恢复；安全副本及普通备份都应支持新数据。

## 9. 建议实施顺序

1. 先实现整数均分、成员汇总及净额结算函数，以示例、尾差和多债权人场景验证守恒。
2. 完成新增数据表、非破坏性迁移和公共费用与个人流水的事务联动。
3. 同步升级备份、恢复及通用编辑／删除入口，避免新功能绕过现有数据保护。
4. 完成事件创建、成员管理、费用录入、事件概览和结算界面，复用现有组件。
5. 执行计算、迁移、事务回滚、备份和 UI 验证，在模拟器检查效果后生成安装包。

## 10. 暂不纳入本版

- 自动支付识别、通知监听、无障碍服务、截图识别。
- 多设备同步、多人远程编辑、账号、邀请链接与云端权限。
- 不均等分摊、多人共同付款、复杂优惠或手续费拆分。
- 实际转账记录、部分还款、已结清状态及已转账后的补差结算。
- 公共退款、成员报销、事件收入和跨事件债务合并；首版不接受负数公共费用。
- 旧个人事件自动转公共事件、旧流水自动推断总额、跨事件迁移公共费用。
- 成员通讯录、收款账户、支付执行、自动汇率及账户余额。

后续多人同步应另立需求，重新分析身份、权限、冲突及个人账本隔离；本版只保留稳定数据 ID，不提前搭建同步基础设施。
